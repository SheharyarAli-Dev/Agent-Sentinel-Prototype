# Technical Note: Operation Identity & Canonical Action Fingerprinting

## Context

This document captures a visible technical note/issue for implementing global idempotency via `operation_id` + canonical action fingerprint across all domains (transaction, cursor, n8n, liveops). This is **not implemented yet** — it is tracked as a future enhancement per the hardening sprint requirements.

---

## Problem Statement

Currently, duplicate suppression is limited to:
- **Transaction domain only**: In-memory `_SEEN_TRANSACTION_IDS` set in `app/policy/attve.py` (resets on restart).
- **Sequential Behaviour**: Per-session trajectory tracking in `app/policy/sequential_behaviour.py` (in-memory, resets on restart).

There is **no cross-domain, durable operation identity** that can:
1. Deduplicate the exact same action submitted multiple times (network retry, UI double-click, agent re-proposal).
2. Correlate related events across adapters (e.g., a Cursor plan step that triggers an n8n workflow that makes a transaction).
3. Provide a stable key for audit linkage, feedback learning, and exactly-once execution semantics.

---

## Proposed Design

### 1. `operation_id` (Client-Provided, Server-Validated)

- **Source**: Generated by the adapter / client at action proposal time.
- **Format**: UUIDv7 (time-ordered) or ULID — sortable, globally unique.
- **Contract**: 
  - Adapter MUST include `operation_id` in `EventCreate.payload.operation_id` for every action.
  - Server validates presence for non-ephemeral sources (transaction, liveops, cursor plans).
  - For ad-hoc single actions (cursor shell), server MAY generate if absent.

### 2. Canonical Action Fingerprint (Server-Computed)

- **Purpose**: Deterministic hash of the action's semantic content, independent of `operation_id`.
- **Algorithm**: 
  ```
  fingerprint = SHA256(
    source + "|" +
    event_type + "|" +
    canonical(payload)
  )
  ```
  Where `canonical(payload)` sorts keys, strips volatile fields (timestamps, UUIDs, session_ids), and normalizes whitespace.

- **Fields Included in Fingerprint**:
  - `event_type`
  - All payload fields EXCEPT: `session_id`, `transaction_id`, `timestamp`, `nonce`, `request_id`, `operation_id`
  - For `steps[]`: each step's `type`, `target`, `description`, `command`, `code` (normalized)

- **Storage**: Persisted on `DecisionORM.fingerprint` (new column, indexed).

### 3. Idempotency Enforcement

| Scenario | Current Behavior | Proposed Behavior |
|----------|------------------|-------------------|
| Same `operation_id` re-submitted | Allowed (new event row) | **409 Conflict** — return existing decision |
| Different `operation_id`, same fingerprint | Allowed | **409 Conflict** — return existing decision (configurable: `fail-open` vs `fail-closed`) |
| `operation_id` missing | Accepted | Generate server-side + warn |

### 4. Cross-Domain Correlation

- When a Cursor plan triggers an n8n workflow: child events inherit parent `operation_id` via `causation_id` field.
- Enables end-to-end trace: `cursor_plan → n8n_workflow → transaction_purchase` all share root `operation_id`.

## Database Changes

```sql
ALTER TABLE decisions ADD COLUMN fingerprint VARCHAR(64);
ALTER TABLE decisions ADD COLUMN operation_id VARCHAR(64);
CREATE INDEX idx_decisions_fingerprint ON decisions(fingerprint);
CREATE UNIQUE INDEX idx_decisions_operation_id ON decisions(operation_id) WHERE operation_id IS NOT NULL;
```

| `liveops_adapter.py` | Generate `operation_id` per LiveOps proposal |

---

## Feedback Learning Impact

- `signature_for()` in `feedback_learning.py` should use `fingerprint` instead of ad-hoc hashing.
- Human decisions on one `operation_id` apply to all future submissions with same fingerprint.

---

## Testing Requirements

1. **Duplicate `operation_id`**: Submit same `operation_id` twice → 409 + existing decision returned.
2. **Same fingerprint, different `operation_id`**: Submit semantically identical action with new ID → 409 (fail-closed) or allow with warning (fail-open).
3. **Cross-adapter correlation**: Cursor plan → n8n → transaction all share root `operation_id`; queryable via audit trail.
4. **Restart persistence**: Fingerprint index survives server restart; in-memory sets do not.

---

## Open Questions

1. **Fail-open vs Fail-closed default**: For production, fail-closed (reject duplicate fingerprint) is safer. For demo, fail-open with warning may be more convenient.
2. **Partial payload matches**: Should `fingerprint` match on subset of fields (e.g., only `event_type` + `target`)? Current design: full canonical payload.
3. **Migration strategy**: Backfill fingerprints for existing decisions? One-time script needed.
